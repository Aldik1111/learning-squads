# Совместная работа

## Начало задачи
1. Сверить main, открытые PR, Issue и владельцев файлов.
2. У каждого своя копия. На одном ПК — разные каталоги/worktree.
3. Обновить чистую локальную main через git pull --ff-only.
4. Создать ветку, например codex/ui-learning или codex/api-invitations.
5. Открыть Draft PR рано. Добавить ссылку на Issue и зависимые PR.

## Координация
Контракты в src/contracts и docs/contracts.md ведёт B с согласованием A.
Миграции, package.json, lock-файл, CI и конфигурация принадлежат B.
layout, globals.css и UI-kit принадлежат A после bootstrap.
Изменение чужого файла заранее согласовать в Issue/PR. Не решать конфликты массовым выбором своей версии.
Раз в два часа: что слито, что блокирует другого, какие общие файлы будут меняться.
Mocks допускаются только для разработки. Подключать реальные блоки по мере готовности.

## Приёмка PR
- Объём соответствует Issue и контракту.
- Выполнены доступные проверки, результат указан.
- Нет секретов, непреднамеренных изменений или выдуманного успеха.
- Второй разработчик просмотрел PR.
- Слияние squash; после слияния проверить функцию на опубликованном сайте, когда он появится.
- Закрыть Issue только после критериев. До приёмки используйте "Refs #...", а не автоматическое "Closes #...".

## Защита main
План настройки: один approve, актуальная ветка, Repository hygiene, разрешённые обсуждения, запрет force push/удаления. Применение и фактический статус — docs/repository-setup.md.
CODEOWNERS обозначает ответственность и запросы ревью. Обязательное code-owner approval выключено: владелец собственных файлов не может одобрить свой PR; проверяет второй разработчик.
GitHub Projects не обязателен: используйте labels status:ready, status:blocked, status:in-progress, status:review. Done = закрытая Issue после проверки.
