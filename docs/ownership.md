## Текущее состояние — 14.11.2026

Bootstrap выполнен: существует одно интегрированное Next.js-приложение. UI-маршруты подключены к общему `src/lib/api-client/index.ts`; HTTP API реализован в `src/app/api/[...path]/route.ts`, серверные правила и доступ — в Supabase RPC/миграциях. Таблица закрепляет ответственность за фактические файлы и будущие расширения; отдельный файл для каждого API endpoint не требуется.

`PythonExercise` находится в области B, принимает согласованный `PythonExerciseData` и возвращает `PythonRunResult`. A подключает компонент в `src/features/learning/ui/learning-page.tsx`, отвечает за сохранение результата через API и отображение состояния. Сигнатуры и ошибки — в `src/contracts/index.ts` и `docs/contracts.md`. Новые зависимости, контракты и миграции координируются с B до изменения.

## Временная параллельная работа

По EXECUTION-001 v1 владелец разрешил текущим назначенным субагентам реализовать области A и B в ветке `codex/a-learning-modules`. Координатор распределяет непересекающиеся файлы, интегрирует результат и фиксирует проверки/SHA в связанных Issues. Это разрешение на текущую работу, а не снятие ответственности B или право перезаписывать его опубликованные изменения. Документы состояния и эта таблица актуализируются по поручению координатора.

В одном worktree изменения сразу видны другим участникам: перед правкой подтвердить владельца задачи, не редактировать одновременно один файл, не запускать массовое форматирование, не выполнять чужие коммиты/сбросы. В обычной работе A и B используют отдельные копии и свои `codex/*`-ветки. Вне таблицы — договориться в связанном Issue до изменения; читать можно все файлы.

Разработка и публикация своей ветки идут без ранних PR. PR открывается перед слиянием готовой части; нужны ревью второго разработчика и действующие проверки, защита main сохраняется. Закрытие задачи требует проверки её критериев, а не только наличия файлов. Публикация ветки, merge и выкладка — разные события.

Распределение не является файловым ограничением GitHub: Write-доступ действует на репозиторий. Принятие приглашения B и проверка его доступа учитываются отдельно в #22; назначение роли в документе не доказывает принятый доступ.
